TURKDEX INSTALL / FIRST DEPLOY SETUP
===================================

Package purpose
---------------
One installation serves ONE EVM chain. The included example targets Turkchain (1919).
For another chain, make a separate installation directory and a separate .env, RPC, API,
contract registry, persistent data directory, domain/TLS setup, and chain-specific tests.
Do not switch chains in the live TurkDex wallet UI.

IMPORTANT CURRENT STATE
-----------------------
This ZIP is a source + ENV + preflight/test package, NOT a currently deployable full DEX release.
The normal installer is expected to stop with exit code 3 because the pinned public Uniswap
interface source declares tools/uniswap-nx and its Nx generators but the package is absent from
the public checkout. Do not remove this guard or fabricate an empty package.

The API copy is also not yet chain-independent: it has Turkchain-only chain checks, RPC/explorer
defaults, registry references, seed data and database constraints. The web source still has
Uniswap-specific service requirements. Production activation is prohibited until these have been
replaced by working TurkDex-owned adapters and all clean install/build/browser/API checks pass.

FIRST INSTALL ON A NEW LINUX SERVER
-----------------------------------
1. Install Node.js 22.22.2 and Bun 1.3.14 or later. Keep package managers pinned to lockfiles.
2. Extract the ZIP into a new versioned directory. Do not overwrite the currently served release.
3. Copy .env.example to .env; chmod 600 .env; edit it on the server. Never include private keys,
   seed phrases, DB passwords or API secrets in this ZIP, VITE_* variables, source control or logs.
4. Fill ONE chain profile: name, decimal/hex chain ID, native token and decimals, RPC, explorer,
   public DEX URL, API URL and all actually deployed protocol addresses. Empty means unavailable.
   Never use zero addresses, Ethereum defaults or guessed addresses.
5. Run: bash scripts/install.sh --env=/absolute/path/.env --validate-only
   This makes read-only eth_chainId and eth_getCode checks. Bytecode presence does not prove ABI,
   version, security or protocol compatibility.
6. Run: bash scripts/install.sh --env=/absolute/path/.env
   With this archive it must stop at the missing official Nx workspace. Do not point Nginx/current
   at this tree until the stop condition has been resolved and all remaining gates pass.
7. After a verified application build exists, configure its service manager, persistent data,
   reverse proxy, TLS and DNS as described below. Run smoke tests, preserve the old release and
   activate by atomic symlink switch. Roll back on any failed smoke test.

ENV FILE VS SERVER/CHAIN CONFIGURATION
--------------------------------------
The .env file stores values that the application can read: chain/RPC identity, app/API URLs,
brand and social URLs, feature flags, gas configuration, contract addresses, and server-side
secret settings if/when the API explicitly supports them. Variable-by-variable descriptions and
which current code consumes them are in docs/ENV_VARIABLES.md.

The following cannot be accomplished by adding an ENV value alone. Configure the named host or
chain resource, then put its resulting URL/path/address in .env where supported:

* DNS: create A/AAAA/CNAME records at the domain DNS provider and point them to the web/API host.
  Current TurkDex already has dex.turkscan.com and dexapi.turkscan.com; no new subdomain is needed
  for the existing topology. DNS changes are made at the domain provider, not in this ZIP.
* TLS certificates: issue certificates for each public hostname and configure Nginx/Caddy paths.
  Certificate private keys stay on the server and are never copied into the archive.
* Nginx/reverse proxy: configure virtual hosts, static root, /api proxy, security headers/CSP,
  body/timeouts, SSE buffering and cache policy in the server's Nginx config. This is not an ENV
  variable and is host-specific. Do not use connect-src *.
* Process/service manager: create a systemd/PM2/container service with a restricted user, working
  directory, restart policy, log policy and EnvironmentFile pointing to the protected .env.
  API listener port/host must match that service and proxy. The copied server currently binds to
  loopback and reads PORT, TURKCHAIN_WS_RPC_URL and TURKDEX_DATA_DIR; many other documented API
  ENV settings are not yet wired into it.
* Persistent storage: create a writable, backed-up data directory outside disposable release
  folders. Set TURKDEX_DATA_DIR only after checking the API's resolved path and ownership. Database
  migrations/schema changes require versioned migration files and rollback planning; do not
  delete or recreate existing indexer databases.
* Application/API implementation: ENV cannot create a missing API route, implement a V2/V3/V4
  router adapter, migrate a database, remove Uniswap gateway calls, add wallet logic, or make a
  chain's contracts compatible. Implement and test these in source first.
* Chain deployments: ENV cannot deploy a contract or prove an address. Obtain addresses from a
  deployment manifest; verify chain ID, bytecode, ABI, constructor/dependency links and protocol
  compatibility. A missing contract stays blank and its feature stays disabled.
* Data sources: price, USD TVL/APR/volume, token logos, analytics and charts need a real, licensed,
  trusted provider or a TurkDex indexer/API implementation. Without one, leave URL blank and show
  no fabricated value. Never substitute an Uniswap-owned data endpoint.
* External provider IDs: WalletConnect needs a project ID created in the operator's WalletConnect
  Cloud account if that connector is enabled. This public project ID goes in WALLETCONNECT_PROJECT_ID.
  Do not use Uniswap telemetry/trading credentials; remove those requirements from the web source.
* Frontend build values: VITE_* variables are public and usually baked into the build. Changing
  them requires a rebuild unless an explicitly implemented runtime-config file is used. Never put
  secrets under VITE_*.
* API secrets: create credentials with the relevant provider/operator and store them in a protected
  server-side EnvironmentFile or secret manager. Do not invent values and do not print them.
* Social/legal URLs: the operator must provide actual TurkDex URLs. Blank variables mean hide the
  link; do not retain a Uniswap URL as a fallback.

KNOWN CONFIGURATION THAT MUST BE IMPLEMENTED BEFORE CLAIMING PORTABILITY
------------------------------------------------------------------------
* The frontend must read ALL product/network/API/explorer/RPC/documentation/social URLs from one
  validated ENV-derived central config, with no browser requests to Uniswap data/gateway/telemetry.
* API, indexer, SDK and frontend must share the same chain config. Current API is hardcoded to
  Chain ID 1919 and its registry/seed/index schema; another EVM chain needs a source migration,
  per-install registry, schema and isolated data—not just changed CHAIN_ID.
* Turkchain's current two V4 pools and existing V2 deployment must be discovered from the configured
  RPC/API. Do not hardcode them as the only pools, and do not invent USD metrics.
* Swap/liquidity execution needs supported route, correct allowance/Permit2, calldata simulation,
  gas estimation, balance checks and user wallet confirmation. Feature flags alone cannot authorize
  a transaction. This installer sends no transaction and deploys no contract.
* Current full interface build is blocked by the absent upstream Nx workspace. Resolve from a
  source-matched/licensed upstream package or a verified compatible public release, then execute
  frozen install, generation, TypeScript, test, production build, API contract tests, browser
  Network audit, wallet simulation and rollback tests.

TEST/PRODUCTION SEPARATION
-------------------------
Use .env.test.example only for isolated tests (local API port 13919, read-only RPC checks, no
production DB/write credentials). Do not point test API writes at production. Tests must not submit
mainnet approvals, swaps or liquidity transactions. Live transaction tests require the user's own
explicit MetaMask approval and are not run by install.sh.
